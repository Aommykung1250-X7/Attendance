# ระบบคำขอลา งานนอกสถานที่ และการเช็กชื่อแบบตรวจพิกัด — เอกสารออกแบบ

วันที่: 2026-09-22
สถานะ: เจ้าของโปรเจกอนุมัติแบบแล้ว

## 1. เป้าหมาย

เปลี่ยนลิงก์พนักงานใน LINE OA จากหน้าขอทำงานนอกสถานที่เพียงอย่างเดียวให้เป็นศูนย์คำขอที่ `/request` หลังล็อกอินด้วย Google และตรวจว่าอีเมลอยู่ในรายชื่อพนักงานที่ยังใช้งานอยู่ พนักงานเลือกยื่นใบลาหรือขอทำงานนอกสถานที่ได้จากหน้าเดียว แอดมินพิจารณาคำขอทุกประเภทจากหน้าหลังบ้านหน้าเดียว

พร้อมกันนี้ ระบบเช็กชื่อผ่าน QR ต้องตรวจว่ามือถืออยู่ภายในรัศมี 200 เมตรจากสำนักงาน ปรับเกณฑ์การมาสายได้จาก Settings และเติมเวลาเช็กเอาต์อัตโนมัติเมื่อเลยเวลาเลิกงาน 5 นาที

เกณฑ์ความสำเร็จ:

- พนักงานยื่น ติดตาม และยกเลิกคำขอที่ยังรออนุมัติได้จาก `/request`
- แอดมินอนุมัติ ปฏิเสธ และจัดการรายการย้อนหลังได้จากหน้าคำขอหน้าเดียว
- การอนุมัติมีผลต่อจอสำนักงาน บันทึกประจำวัน และรายงานโดยไม่ต้องแก้สถานะซ้ำ
- ผู้ที่ไม่สามารถยืนยันตำแหน่งภายในเงื่อนไขที่กำหนดเช็กอินด้วย QR ไม่ได้
- เวลาเข้างาน สถานะครึ่งวัน และเวลาเช็กเอาต์อัตโนมัติคำนวณเหมือนกันทุกหน้า

## 2. ขอบเขตและคำตัดสินที่ยืนยันแล้ว

### 2.1 การลา

- พนักงานยื่นได้ตั้งแต่วันปัจจุบันเป็นต้นไป ห้ามยื่นย้อนหลัง
- เลือกลา 1 วันหรือช่วงหลายวันได้
- การลาหลายวันเป็นลาเต็มวันทุกวัน
- การลา 1 วันเลือกเต็มวัน ครึ่งเช้า หรือครึ่งบ่ายได้
- การลาครึ่งวันไม่เลือกประเภทลา ต้องเลือกครึ่งเช้าหรือครึ่งบ่ายและกรอกเหตุผล
- การลาเต็มวันเลือก `ลาป่วย` หรือ `ลากิจ` และกรอกเหตุผล
- ลาป่วยแนบใบรับรองแพทย์ได้ทันที หรือเลือกว่าจะนำส่งภายหลัง
- ลากิจไม่ต้องแนบเอกสาร
- พนักงานยกเลิกได้เฉพาะคำขอที่ยังรออนุมัติ
- แอดมินเพิ่ม แก้ หรือยกเลิกรายการย้อนหลังได้ โดยทุกการเปลี่ยนแปลงมี Audit log
- คำขอหลายวันอนุมัติหรือปฏิเสธทั้งชุด ไม่อนุมัติแยกรายวัน

### 2.2 ครึ่งวันและเวลาพัก

- เวลาพักกลางวันคือ 12:00–13:00
- เวลาเริ่มงานช่วงบ่ายคือ 13:00
- ผู้ที่ลาครึ่งเช้าต้องเช็กอินตั้งแต่ 13:00 และใช้ค่าผ่อนผันการมาสายเดียวกับกะปกติ
- ผู้ที่ลาครึ่งบ่ายต้องเช็กอินช่วงเช้าตามกะปกติ ตั้งแต่ 13:00 จอแสดงว่าลาครึ่งบ่าย
- ผู้ลาครึ่งบ่ายได้รับเวลาเช็กเอาต์อัตโนมัติเป็นเวลาเลิกงานตามกะ

### 2.3 งานนอกสถานที่

- ยื่นได้เฉพาะวันปัจจุบัน
- ต้องเลือกกะ ระบุสิ่งที่จะทำ ระบุสถานที่ แนบรูป และแชร์ตำแหน่ง
- แอดมินอนุมัติหรือปฏิเสธพร้อมเหตุผลได้
- เมื่ออนุมัติ ระบบบันทึก Attendance เป็นสถานะทำงานนอกสถานที่

### 2.4 การตรวจตำแหน่งตอนเช็กอิน

- ตรวจเฉพาะตอนเช็กอิน ไม่ตรวจตอนเช็กเอาต์
- จุดศูนย์กลางเริ่มต้นคือ `18.800523577253724, 98.95073601100776`
- ระยะที่อนุญาตเริ่มต้นคือ 200 เมตร
- ค่าความคลาดเคลื่อนของ GPS ต้องไม่เกิน 100 เมตร
- หากผู้ใช้ไม่อนุญาตตำแหน่ง ปิด GPS จับตำแหน่งไม่ได้ ค่าความคลาดเคลื่อนสูงเกินไป หรืออยู่นอกพื้นที่ ให้ปฏิเสธการเช็กอินและแจ้งให้เปิดตำแหน่ง
- หน้าจอมีปุ่ม “ลองจับตำแหน่งใหม่” และไม่ใช้สิทธิ์การสแกนจนกว่าเช็กอินสำเร็จ

### 2.5 เวลาและการเช็กเอาต์

- หน้า Settings เพิ่มจำนวนนาทีที่อนุโลมให้มาสายได้ ช่วงค่าที่รับคือ 0–120 นาที
- เมื่อมี Attendance ที่เช็กอินแล้วแต่ยังไม่เช็กเอาต์ และเลยเวลาเลิกงาน 5 นาที ระบบเติมเวลาออกเป็นเวลาเลิกงานตามกะ
- รายการอัตโนมัติระบุ `checkedOutBy = system` เพื่อแยกจากพนักงานและแอดมิน

## 3. สถาปัตยกรรมที่เลือก

ใช้ “ศูนย์คำขอหน้าเดียว แต่แยกตารางตามประเภท” เนื่องจากใบลาและงานนอกสถานที่มีฟิลด์ กติกา และผลต่อ Attendance ต่างกันมาก

ส่วนประกอบหลัก:

1. `Request` ฝั่งพนักงาน: landing page, ฟอร์มลา, ฟอร์มงานนอกสถานที่ และประวัติคำขอของตนเอง
2. `Admin Requests`: inbox กลางสำหรับค้นหา กรอง และพิจารณาคำขอทุกประเภท
3. `Leave service`: ตรวจวัน สร้างวันลารายกะ ตรวจคำขอชนกัน และประยุกต์ผลอนุมัติกับสถานะประจำวัน
4. `Offsite service`: ใช้ตรรกะงานนอกสถานที่เดิม แต่ย้ายเข้าโครงสร้าง Request กลาง
5. `Attendance policy`: จุดเดียวสำหรับเกณฑ์สาย เวลาเริ่มช่วงบ่าย สถานะครึ่งวัน และเวลาออกอัตโนมัติ
6. `Geofence service`: ตรวจ accuracy และคำนวณระยะจากพิกัดสำนักงานฝั่งเซิร์ฟเวอร์
7. `Auto-checkout worker`: เติมเวลาออกที่ขาดหายแบบ idempotent ทุกนาทีและเมื่อเซิร์ฟเวอร์เริ่ม

ไม่มีเส้นทาง `/offsite` ในผลิตภัณฑ์ใหม่ เพราะลิงก์เดิมยังไม่ได้ใช้งานจริง เส้นทางพนักงานคือ `/request` เท่านั้น

## 4. แบบจำลองข้อมูล

### 4.1 `leave_requests`

หนึ่งแถวแทนคำขอหนึ่งชุด:

- `id`
- `employee_id`
- `start_date`
- `end_date`
- `duration`: `full_day | morning | afternoon`
- `leave_type`: `sick | personal | null` โดยครึ่งวันต้องเป็น `null`
- `reason`
- `medical_certificate_path`: nullable
- `medical_certificate_pending`: boolean
- `medical_certificate_received_at`: nullable
- `status`: `pending | approved | rejected | cancelled`
- `reviewed_by`, `reviewed_at`, `reject_reason`
- `cancelled_at`
- `created_at`, `updated_at`

ข้อบังคับระดับ service และฐานข้อมูล:

- `start_date <= end_date`
- ถ้า `start_date != end_date` ต้องเป็น `full_day`
- `full_day` ต้องมี `leave_type`
- `morning` และ `afternoon` ต้องไม่มี `leave_type`
- ลาป่วยต้องมีไฟล์หรือ `medical_certificate_pending = true`
- ลากิจและครึ่งวันต้องไม่ตั้ง `medical_certificate_pending`

### 4.2 `leave_request_days`

แตกช่วงวันลาเป็นรายการที่มีผลต่อกะจริง:

- `id`
- `leave_request_id`
- `employee_id`
- `shift_id`
- `date`
- `portion`: `full_day | morning | afternoon`

มี unique constraint ที่ `(leave_request_id, shift_id, date)` วันหยุดและวันที่ไม่มีกะจะไม่สร้างรายการ ตารางนี้ทำให้หน้าจอและรายงานอ่านผลลาได้โดยไม่ต้องตีความช่วงวันที่ซ้ำ

### 4.3 `offsite_requests`

คงตารางและข้อมูลที่มีอยู่ ได้แก่ พนักงาน กะ วันที่ งาน รูป พิกัด ชื่อสถานที่ สถานะ และข้อมูลผู้พิจารณา เพิ่ม `updated_at` และสถานะ `cancelled` เพื่อให้พนักงานยกเลิกรายการรออนุมัติได้

### 4.4 `attendance`

เพิ่ม:

- `checkin_latitude`, `checkin_longitude`: nullable เพื่อรองรับข้อมูลเดิมและรายการที่แอดมินบันทึก
- `checkin_accuracy_meters`: nullable
- `checkin_distance_meters`: nullable
- `checked_out_by` รองรับ `self | system | <admin email>`

ไม่สร้าง Attendance ปลอมสำหรับการลาเต็มวัน สถานะลามาจากใบลาที่อนุมัติแล้ว ส่วนงานนอกสถานที่ยังสร้าง Attendance เนื่องจากถือว่าเข้าทำงาน

### 4.5 `settings`

เพิ่ม:

- `late_grace_minutes` ค่าเริ่มต้น 0
- `office_latitude` ค่าเริ่มต้น `18.800523577253724`
- `office_longitude` ค่าเริ่มต้น `98.95073601100776`
- `checkin_radius_meters` ค่าเริ่มต้น 200
- `max_location_accuracy_meters` ค่าเริ่มต้น 100

พิกัด รัศมี และ accuracy แก้ได้จากหน้า Settings เพื่อรองรับการย้ายสำนักงานหรือปรับนโยบายโดยไม่แก้โค้ด

## 5. สถานะประจำวัน

สถานะเข้างานและส่วนของวันที่ลาเป็นข้อมูลคนละแกน:

- `status`: `ontime | late | absent | leave | pending | offsite`
- `leavePortion`: `full_day | morning | afternoon | null`

กติกาแสดงผล:

| กรณี | ก่อน 13:00 | ตั้งแต่ 13:00 | หลังจบกะ |
|---|---|---|---|
| ลาเต็มวัน | ลา | ลา | ลา |
| ลาครึ่งเช้า ยังไม่เช็กอิน | ลาครึ่งเช้า | ยังไม่มา/สายตามเวลา | ขาดช่วงทำงานหากไม่มา |
| ลาครึ่งเช้า เช็กอินแล้ว | ลาครึ่งเช้า | ปกติหรือสาย พร้อมป้ายลาครึ่งเช้า | ปกติ/สาย พร้อมเวลาออก |
| ลาครึ่งบ่าย เช็กอินช่วงเช้า | ปกติหรือสาย | ลาครึ่งบ่าย | เช็กเอาต์ตามเวลาเลิกกะ |
| ลาครึ่งบ่าย ไม่เช็กอิน | ยังไม่มา/สายตามเวลา | ลาครึ่งบ่าย แต่เก็บว่าขาดช่วงเช้า | ขาดช่วงทำงานและลาครึ่งบ่าย |

จอสำนักงานต้องแสดงป้ายครึ่งวันควบคู่กับผลเข้างาน เพื่อไม่ทำให้ข้อมูลครึ่งวันที่มาทำงานหายไป

รายงานรายเดือนเพิ่มยอด:

- ลาเต็มวัน
- ลาครึ่งเช้า
- ลาครึ่งบ่าย

ครึ่งวันไม่ถูกนับเป็นลาเต็มวันหนึ่งวัน และผลปกติ/สาย/ขาดของช่วงที่ต้องทำงานยังคงถูกนับ

## 6. กติกาเวลา

### 6.1 การมาสาย

- กะปกติใช้เวลาเริ่มกะ
- ลาครึ่งเช้าใช้ 13:00 เป็นเวลาเริ่มที่มีผล
- เส้นตายคือเวลาเริ่มที่มีผลบวก `late_grace_minutes`
- การสแกนภายในนาทีสุดท้ายของช่วงผ่อนผันถือว่าปกติ ตั้งแต่นาทีถัดไปถือว่าสาย

ตัวอย่าง: เริ่ม 09:30 ผ่อนผัน 10 นาที เวลา 09:40:59 ยังปกติ และ 09:41:00 เป็นต้นไปถือว่าสาย

### 6.2 เช็กเอาต์อัตโนมัติ

worker ทำงานทุกนาทีและเมื่อเซิร์ฟเวอร์เริ่ม:

1. หา Attendance ที่มี `scanned_at` แต่ไม่มี `checked_out_at`
2. โหลดเวลาเลิกงานของกะและวันที่รายการนั้น
3. เมื่อเวลาปัจจุบันตั้งแต่เวลาเลิกงานบวก 5 นาที ให้ตั้ง `checked_out_at` เป็นเวลาเลิกงานตามกะ
4. ตั้ง `checked_out_by = system`
5. อัปเดตเฉพาะแถวที่ยังไม่มีเวลาออก จึงรันซ้ำได้อย่างปลอดภัย

การรันตอนเริ่มระบบทำให้ข้อมูลย้อนหลังครบแม้เซิร์ฟเวอร์หยุดในช่วงเวลาเลิกงาน

## 7. Flow ฝั่งพนักงาน

### 7.1 หน้า `/request`

1. ลิงก์ LINE OA เปิด `/request`
2. ถ้ายังไม่ล็อกอิน ให้เข้า Google OAuth และกลับมาหน้าเดิม
3. ตรวจอีเมลกับพนักงานที่ active ห้ามสร้างพนักงานอัตโนมัติ
4. แสดงชื่อพนักงาน สองตัวเลือก “ยื่นลา” และ “ขอทำงานนอกสถานที่” พร้อมรายการคำขอล่าสุด

### 7.2 ยื่นลา

1. เลือก 1 วันหรือช่วงวัน
2. วันที่ต่ำสุดคือวันปัจจุบัน
3. หากวันเดียว เลือกเต็มวัน ครึ่งเช้า หรือครึ่งบ่าย
4. หากหลายวัน ระบบกำหนดเต็มวันและไม่แสดงตัวเลือกครึ่งวัน
5. เต็มวันเลือกประเภทลา ครึ่งวันไม่เลือกประเภท
6. กรอกเหตุผล
7. ลาป่วยแนบใบรับรองหรือเลือกส่งภายหลัง
8. แสดงหน้าสรุปจำนวนวันที่มีกะจริง วันที่ไม่มีตารางงาน และข้อมูลที่จะส่ง
9. ตรวจคำขอชนกันอีกครั้งแล้วบันทึกเป็น `pending`

### 7.3 งานนอกสถานที่

1. โหลดกะของวันปัจจุบัน
2. เลือกกะหากมีหลายกะ
3. กรอกงานและสถานที่
4. แนบรูป
5. ขอพิกัดปัจจุบัน
6. แสดงสรุปและส่งเป็น `pending`

พิกัดของงานนอกสถานที่เป็นหลักฐานตำแหน่งที่พนักงานเลือกทำงาน ไม่ใช้กฎรัศมีสำนักงาน

### 7.4 ติดตามและยกเลิก

- พนักงานดูสถานะ เหตุผลปฏิเสธ และเอกสารของตนเองได้
- ปุ่มยกเลิกแสดงเฉพาะสถานะ `pending`
- การยกเลิกใช้ compare-and-update เพื่อกันคำขอถูกอนุมัติพร้อมกัน
- ลาป่วยที่รอเอกสารสามารถอัปโหลดเอกสารภายหลังได้ แม้คำขอได้รับอนุมัติแล้ว

## 8. Flow ฝั่งแอดมิน

หน้า `/admin/requests` รวมสองประเภทและแทนหน้า Offsite Requests เดิม

- แท็บ: รอดำเนินการ, อนุมัติแล้ว, ปฏิเสธ/ยกเลิก, ทั้งหมด
- กรองตามประเภท วันที่ และพนักงาน
- เมนูแสดงจำนวนคำขอรอดำเนินการ
- แถวสรุปแสดงประเภท ชื่อ วันที่ ช่วงเวลา และสถานะ
- drawer/modal รายละเอียดแสดงเหตุผล เอกสาร รูป แผนที่ และ Audit log
- ปฏิเสธต้องมีเหตุผล
- การอนุมัติและยกเลิกใช้ transaction และตรวจสถานะปัจจุบันก่อนเขียน

การจัดการย้อนหลัง:

- แอดมินสร้างคำขอลาที่อนุมัติแล้วสำหรับอดีตได้
- แอดมินแก้วัน รูปแบบ ประเภท เหตุผล และสถานะเอกสารได้
- ก่อนแก้ต้องตรวจการทับซ้อนใหม่
- การแก้คำขอที่อนุมัติแล้วสร้าง `leave_request_days` ใหม่ใน transaction เดียวกัน
- การยกเลิกรายการที่อนุมัติแล้วเอาผลลาออกจากวันและรายงานทันที
- ทุกการเพิ่ม แก้ อนุมัติ ปฏิเสธ ยกเลิก รับเอกสาร หรืออัปโหลดเอกสารบันทึก Audit log

## 9. การตรวจคำขอชนกัน

ห้ามมีคำขอ `pending` หรือ `approved` ที่ใช้พนักงาน กะ และวันเดียวกันซ้อนกันระหว่าง:

- ใบลากับใบลา
- ใบลากับงานนอกสถานที่
- งานนอกสถานที่กับงานนอกสถานที่

รายการ `rejected` และ `cancelled` ไม่ขวางการยื่นใหม่ ตรวจทั้งตอนสร้างและตอนอนุมัติ ภายใน transaction เดียวกับการเปลี่ยนสถานะ เพื่อลด race condition

หากช่วงวันที่เลือกไม่มีวันทำงานเลย ให้ปฏิเสธคำขอพร้อมข้อความให้เลือกวันที่มีตารางงาน หากมีทั้งวันทำงาน วันหยุด และวันที่ไม่มีกะ ให้สร้างเฉพาะวันทำงานและแสดงสรุปก่อนส่ง

## 10. การตรวจพิกัด QR

### 10.1 ฝั่งเบราว์เซอร์

ใช้ Geolocation API ด้วยค่าประมาณนี้:

- `enableHighAccuracy: true`
- `maximumAge: 0`
- `timeout: 15000`

หน้าเช็กอินส่ง `latitude`, `longitude` และ `accuracy` ไปกับคำขอยืนยัน ห้ามให้ค่าจาก client เป็นผู้ตัดสินผล

### 10.2 ฝั่งเซิร์ฟเวอร์

1. ตรวจว่าค่าทั้งหมดเป็นเลขและอยู่ในช่วงพิกัดที่ถูกต้อง
2. ตรวจ `accuracy <= max_location_accuracy_meters`
3. คำนวณ Haversine distance จากพิกัดใน Settings
4. ตรวจ `distance <= checkin_radius_meters`
5. เมื่อผ่านจึงบันทึก Attendance พร้อมพิกัด accuracy และระยะที่เซิร์ฟเวอร์คำนวณ

เมื่อไม่ผ่านทุกกรณี ตอบ error code ที่ frontend แปลงเป็นข้อความเดียว:

> ไม่สามารถยืนยันตำแหน่งสำหรับเช็กอินได้ กรุณาเปิดตำแหน่งบนโทรศัพท์และลองใหม่อีกครั้ง

พร้อมปุ่ม “ลองจับตำแหน่งใหม่” การตรวจไม่ผ่านไม่ตั้ง `usedAt` ใน scan session จึงลองใหม่ได้จน session หมดอายุ

การตรวจเว็บ GPS ลดการเช็กอินจากนอกพื้นที่ทั่วไป แต่ไม่รับประกันการป้องกันแอปปลอมพิกัดบนอุปกรณ์ที่ถูกดัดแปลง

## 11. API ที่เสนอ

### 11.1 พนักงาน

- `GET /api/requests/me` — ข้อมูลพนักงาน กะวันนี้ และคำขอล่าสุด
- `POST /api/requests/leave` — สร้างใบลา รองรับ multipart เมื่อมีไฟล์
- `POST /api/requests/offsite` — สร้างคำของานนอกสถานที่แบบ multipart
- `POST /api/requests/leave/:id/cancel`
- `POST /api/requests/offsite/:id/cancel`
- `POST /api/requests/leave/:id/medical-certificate`
- `GET /api/requests/files/:fileId` — ตรวจว่าเป็นเจ้าของหรือแอดมินก่อนส่งไฟล์

### 11.2 แอดมิน

- `GET /api/admin/requests` — รายการรวมพร้อม filter และ pagination
- `POST /api/admin/requests/leave/:id/review`
- `POST /api/admin/requests/offsite/:id/review`
- `POST /api/admin/requests/leave` — สร้างย้อนหลัง
- `PATCH /api/admin/requests/leave/:id` — แก้ไข
- `POST /api/admin/requests/leave/:id/cancel`
- `POST /api/admin/requests/leave/:id/mark-document-received`

### 11.3 เช็กชื่อและ Settings

- `POST /api/checkin` เพิ่ม location object ใน body
- `GET/PATCH /api/admin/settings` เพิ่มค่าผ่อนผันและ geofence

API ตอบรหัส error ที่คงที่สำหรับ frontend และข้อความภาษาไทยสำหรับผู้ใช้ แต่ไม่เปิดรายละเอียดพิกัดหรือระยะในข้อความปฏิเสธ

## 12. ไฟล์แนบและสิทธิ์

- รูปงานนอกสถานที่รับ JPG, JPEG, PNG และ WebP
- ใบรับรองแพทย์รับ PDF, JPG, JPEG และ PNG
- จำกัดขนาดไฟล์ละ 5 MB
- ใช้ชื่อไฟล์แบบสุ่มและไม่ใช้ชื่อไฟล์จากผู้ใช้เป็น path
- ไม่ตรวจ MIME signature หรือวิเคราะห์เนื้อหา แอดมินตรวจเอกสารจากไฟล์ที่เปิดดู
- endpoint ไฟล์ตรวจว่าเป็นเจ้าของคำขอหรือแอดมิน ห้ามเสิร์ฟใบรับรองแพทย์เป็นไฟล์สาธารณะ
- กำหนด `Content-Disposition: inline` สำหรับชนิดที่เบราว์เซอร์เปิดได้ และ `X-Content-Type-Options: nosniff`

## 13. การแจ้งผลและ UX ข้อผิดพลาด

- หน้า `/request` แสดงสถานะล่าสุดโดยไม่ต้องพึ่งข้อความจากระบบภายนอก
- หน้าแอดมินโหลดจำนวนคำขอรอดำเนินการเป็นระยะเพื่ออัปเดต badge
- ไม่มี LINE push notification ในขอบเขตนี้
- แบบฟอร์มเก็บค่าที่กรอกไว้เมื่อเกิด validation error
- ปุ่มส่งป้องกันการกดซ้ำและ API ใช้ข้อบังคับฐานข้อมูล/transaction ป้องกันรายการซ้ำ
- หาก session หมดอายุ ให้ล็อกอินใหม่และกลับหน้าที่เหมาะสม
- หาก auto-checkout ล้มเหลวหนึ่งรอบ ให้บันทึก error และลองใหม่รอบถัดไป

## 14. การย้ายจากโค้ดปัจจุบัน

โค้ดงานนอกสถานที่ปัจจุบันยังเป็นการเปลี่ยนแปลงที่ไม่ได้ commit จึงต้องย้ายอย่างระมัดระวังและไม่ทำลายงานเดิม:

1. สร้าง migration ใหม่ ห้ามแก้ migration ที่ถูกใช้แล้ว
2. เพิ่มตารางลาและฟิลด์ใหม่ใน Attendance/Settings
3. ย้าย route `/api/offsite/*` ไป namespace `/api/requests/offsite/*`
4. เปลี่ยนหน้า `OffsiteRequest` เป็นหน้า `Request` ที่มีตัวเลือกสองประเภท
5. เปลี่ยนหน้า `Admin OffsiteRequests` เป็น `Admin Requests`
6. ปรับ type contract ทั้ง frontend/backend และใช้สคริปต์ sync ที่มีอยู่
7. คงข้อมูล `offsite_requests` เดิม ไม่ลบหรือสร้างใหม่
8. เปลี่ยนลิงก์ navigation และเอกสาร deployment ให้ชี้ `/request`

## 16. ชุดทดสอบขั้นต่ำ

### Unit tests

- วันที่เริ่ม/สิ้นสุด ช่วงหลายวัน วันหยุด และวันที่ไม่มีกะ
- full day, morning, afternoon และกฎชนิดลา
- คำขอชนกันทุกคู่ประเภท
- เวลา 13:00 และค่าผ่อนผันที่ขอบเขตวินาที
- Haversine ที่ระยะต่ำกว่า เท่ากับ และมากกว่า 200 เมตร
- accuracy ต่ำกว่า เท่ากับ และมากกว่า 100 เมตร
- การคำนวณเวลาเช็กเอาต์ตามกะข้ามกรณีเวลาและวัน

### API/integration tests

- อีเมลไม่ลงทะเบียนและพนักงาน inactive
- พนักงานยื่นย้อนหลังไม่ได้ แอดมินทำได้
- สร้าง อนุมัติ ปฏิเสธ ยกเลิก และ race ระหว่างยกเลิก/อนุมัติ
- อนุมัติช่วงหลายวันแล้วสร้างวันลาเฉพาะวันที่มีกะ
- ลาป่วยแบบแนบไฟล์และส่งภายหลัง
- เจ้าของเปิดไฟล์ได้ บุคคลอื่นเปิดไม่ได้ แอดมินเปิดได้
- เช็กอินผ่าน/ไม่ผ่าน geofence และการลองใหม่ไม่ใช้ scan session
- auto-checkout ทำงานซ้ำได้และตามเก็บหลัง restart
- แก้คำขออนุมัติย้อนหลังแล้ว kiosk/report เปลี่ยนตาม

### Regression tests

- QR token และ scan session
- Google OAuth และการกลับ URL เดิม
- เช็กอิน เช็กเอาต์ และออกก่อนเวลาแบบเดิม
- งานนอกสถานที่เดิมและการอนุมัติ
- หน้าจอสำนักงาน บันทึกประจำวัน และรายงานรายเดือน
- frontend typecheck/build และ backend typecheck/test

## 17. Rollout และการย้อนกลับ

- สำรอง PostgreSQL ก่อน migration
- migration เป็นแบบเพิ่มตาราง/คอลัมน์ ไม่ลบข้อมูลเดิม
- deploy backend ที่อ่านค่า default ได้ก่อน แล้วจึง deploy frontend
- ทดสอบ `/request`, `/checkin`, `/admin/requests`, kiosk และ report บน production domain
- หาก UI ใหม่มีปัญหา สามารถ rollback frontend ได้โดย schema ใหม่ยังไม่กระทบข้อมูลเดิม
- หาก worker มีปัญหา ปิด worker ได้โดยไม่กระทบการเช็กเอาต์ด้วยตนเอง แล้วแก้ข้อมูลที่ขาดผ่าน startup reconciliation หลังแก้ไข
