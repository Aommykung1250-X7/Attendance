# Request Workflow Follow-up Design

วันที่: 22 กันยายน 2026

## เป้าหมาย

ปรับประสบการณ์ใช้งานคำขอของพนักงานและแอดมินหลังการทดลองใช้จริง โดยทำให้ผลของการแก้ตารางกะเข้าใจได้ชัดเจน ลดข้อมูลที่ไม่จำเป็นจากคำขอทำงานนอกสถานที่ และทำให้แอดมินตรวจรายละเอียดคำขอได้ก่อนตัดสินใจ

## ขอบเขต

1. อธิบายผลของการแก้เวลากะเมื่อวันนี้มีการเช็กชื่อแล้ว
2. เปลี่ยนรายการคำขอแอดมินเป็นการ์ดสรุปที่เปิดรายละเอียดแบบ modal ได้
3. ให้การลาครึ่งวันเลือกประเภทลาป่วยหรือลากิจ
4. ใช้กติกาใบรับรองแพทย์กับลาป่วยครึ่งวันด้วย
5. ยกเลิกการเก็บ GPS ของคำขอทำงานนอกสถานที่และลบข้อมูล GPS เดิม
6. ทำปุ่มเลือกไฟล์ให้เห็นว่าโต้ตอบได้ชัดเจน

## 1. การแก้ตารางกะ

คงหลักการรักษาประวัติเดิม:

- ถ้าวันนี้ยังไม่มีการเช็กชื่อ การแก้ตารางกะมีผลวันนี้
- ถ้าวันนี้มีการเช็กชื่อแล้ว กะเดิมยังใช้จนจบวันนี้ และกะใหม่เริ่มใช้วันถัดไป
- ไม่ย้าย attendance ของวันนี้ไปยังกะใหม่และไม่แก้ประวัติย้อนหลัง

หลังบันทึก API ต้องส่งข้อมูลวันที่เริ่มใช้กลับมาให้ frontend แสดงข้อความที่ชัดเจน เช่น:

> บันทึกแล้ว — กะใหม่เริ่มใช้วันที่ 23/09/2026 เนื่องจากวันนี้มีการเช็กชื่อแล้ว

หน้าตารางกะต้องแสดงหมายเหตุเมื่อกะเดิมยังมีผลจนจบวันนี้ เพื่อไม่ให้ผู้ใช้เข้าใจว่าการบันทึกล้มเหลว

## 2. รายการและรายละเอียดคำขอของแอดมิน

### การ์ดสรุป

แต่ละการ์ดแสดงเฉพาะข้อมูลที่ใช้สแกนรายการ:

- ชื่อพนักงาน
- ประเภท: ลาป่วย, ลากิจ, ลาป่วยครึ่งเช้า, ลากิจครึ่งเช้า, ลาป่วยครึ่งบ่าย, ลากิจครึ่งบ่าย หรือทำงานนอกสถานที่
- วันที่หรือช่วงวันที่
- สถานะคำขอ
- ปุ่มดำเนินการที่ใช้ได้กับสถานะปัจจุบัน

พื้นที่หลักของการ์ดเป็นปุ่มเปิดรายละเอียด ใช้งานด้วยคีย์บอร์ดได้ และมี focus style ที่มองเห็นชัด ปุ่มดำเนินการภายในการ์ดต้องไม่ทำให้ modal เปิดโดยไม่ตั้งใจ

### Modal รายละเอียด

เมื่อกดการ์ด ให้เปิด modal แบบ read-only ซึ่งจัดข้อมูลคล้ายฟอร์มตอนพนักงานยื่น แต่แสดงเฉพาะค่าที่เลือกหรือกรอกไว้จริง:

- คำขอลา: วันที่, ช่วงเวลา, ประเภทลา, เหตุผล และข้อมูลใบรับรองแพทย์เมื่อเกี่ยวข้อง
- งานนอกสถานที่: กะ, สิ่งที่จะทำ, ชื่อสถานที่ และรูปหลักฐาน
- ไม่แสดงช่องว่างหรือหัวข้อที่ไม่เกี่ยวข้องกับคำขอนั้น

Modal ปิดได้ด้วยปุ่มปิด, Escape และคลิกฉากหลัง พร้อมจำกัดความสูงและเลื่อนเนื้อหาภายในบนจอเล็ก

### ปุ่มดำเนินการสองตำแหน่ง

ปุ่มอนุมัติ, ปฏิเสธ, ยืนยันรับเอกสาร และยกเลิก แสดงได้ทั้งบนการ์ดและใน modal ตามสิทธิ์และสถานะเดียวกัน ทั้งสองตำแหน่งเรียก action เดียวกัน:

- ระหว่างส่งคำสั่ง ให้ disable ปุ่มที่เกี่ยวข้องทั้งสองตำแหน่ง
- เมื่อสำเร็จ ให้รีโหลดข้อมูลรายการเดียวกัน อัปเดตการ์ดและ modal พร้อมกัน
- การปฏิเสธยังต้องกรอกเหตุผล
- ห้ามส่ง action ซ้ำจากการกดเร็วหรือกดจากสองตำแหน่งติดกัน

## 3. กติกาการลา

ทุกช่วงเวลาต้องเลือกประเภทลา:

- เต็มวัน: ลาป่วยหรือลากิจ
- ครึ่งเช้า: ลาป่วยหรือลากิจ
- ครึ่งบ่าย: ลาป่วยหรือลากิจ
- ช่วงหลายวันยังเป็นลาเต็มวันทุกวัน และต้องเลือกประเภทลา

กติกาใบรับรองแพทย์ใช้กับลาป่วยทุกช่วงเวลา:

- แนบใบรับรองแพทย์ตอนยื่นได้ หรือ
- เลือกว่าจะนำใบรับรองแพทย์มาส่งภายหลัง
- ถ้าเลือกส่งภายหลัง แอดมินกด “ยืนยันรับเอกสาร” เพื่อปิดสถานะรอเอกสาร
- ลากิจไม่แสดงส่วนใบรับรองแพทย์

Backend ต้องตรวจเงื่อนไขเหล่านี้เอง ไม่เชื่อเฉพาะค่าที่ frontend ส่งมา

## 4. คำขอทำงานนอกสถานที่

ข้อมูลที่ต้องกรอก:

- กะของวันนี้
- สิ่งที่จะทำ
- ชื่อสถานที่
- รูปถ่ายหลักฐาน

ยกเลิกข้อมูล GPS ทั้งหมดของคำขอทำงานนอกสถานที่:

- ลบปุ่มจับหรือแชร์ตำแหน่งจาก frontend
- ไม่ส่ง latitude/longitude ใน API
- ลบการบังคับตรวจ latitude/longitude ใน backend
- ลบลิงก์ดูแผนที่ในหน้าแอดมิน
- migration ลบคอลัมน์ `latitude` และ `longitude` จาก `offsite_requests` พร้อมข้อมูลเดิมทั้งหมด
- contract และ mock data ต้องไม่มีสองฟิลด์นี้

การเปลี่ยนนี้ไม่กระทบ GPS geofence ของการเช็กอินด้วย QR ซึ่งยังต้องตรวจตำแหน่งภายใน 200 เมตรตามเดิม

## 5. การเลือกไฟล์

ช่องเลือกไฟล์รูปหลักฐานและใบรับรองแพทย์ต้องเป็นพื้นที่กดที่เห็นชัด:

- มีกรอบ, label และสถานะ hover/focus
- พื้นที่กดเหมาะกับมือถือ
- หลังเลือกแล้วแสดงชื่อไฟล์
- มีข้อความชนิดไฟล์ที่รองรับ
- backend ยังคงตรวจชนิดไฟล์จากเนื้อหาจริง ไม่เชื่อเพียงนามสกุล
- ไม่มีการเพิ่มข้อจำกัดขนาดไฟล์ใหม่ในงานนี้

## 6. การเปลี่ยนฐานข้อมูลและ API

- เพิ่ม migration เพื่อลบ `offsite_requests.latitude` และ `offsite_requests.longitude`
- ปรับชนิดข้อมูล `OffsiteRequest` ทั้ง backend/frontend
- ปรับ create offsite request endpoint ให้ไม่รับ GPS
- ปรับ leave validation ให้ `leaveType` จำเป็นสำหรับทุก duration
- ปรับ medical certificate validation ให้ลาป่วยครึ่งวันใช้กติกาเดียวกับลาป่วยเต็มวัน
- เพิ่มผลลัพธ์จากการบันทึกตารางกะเพื่อบอกวันที่เริ่มมีผลและเหตุผลที่เลื่อนไปวันถัดไป
- คงรูปแบบ endpoint และสิทธิ์เดิมเท่าที่ทำได้ เพื่อลดผลกระทบกับหน้าอื่น

## 7. Error Handling และ State

- การ์ดและ modal ต้องใช้ loading state ร่วมกันระหว่าง action
- เมื่อ action ล้มเหลว ให้คง modal และข้อมูลเดิมไว้ พร้อมแสดง toast error
- รูปหลักฐานโหลดไม่ได้ให้แสดงข้อความแทน ไม่ทำให้ modal พัง
- การ reload อัตโนมัติทุก 5 วินาทียังคงทำงาน และต้องไม่ปิด modal โดยไม่จำเป็น หากคำขอยังอยู่ให้แทนที่ข้อมูลด้วยเวอร์ชันล่าสุด
- หากคำขอถูกเปลี่ยนสถานะจากอีกหน้าต่าง ปุ่มใน modal ต้องปรับตามสถานะล่าสุด

## 8. การทดสอบ

- Logic test: แก้กะก่อนเช็กชื่อมีผลวันนี้
- Logic/integration test บน test database แยก: แก้กะหลังเช็กชื่อมีผลวันถัดไปและรายงาน effective date ถูกต้อง
- Validation test: ลาป่วยและลากิจสำหรับเต็มวัน, ครึ่งเช้า และครึ่งบ่าย
- Validation test: ลาป่วยครึ่งวันแนบเอกสารหรือเลือกส่งภายหลังได้
- Validation test: ลากิจไม่มี medical-certificate state
- API test: สร้างคำขอนอกสถานที่โดยไม่มี GPS
- Migration verification: คอลัมน์และข้อมูล GPS เดิมถูกลบ
- UI test/manual verification: การ์ดเปิด modal, ปุ่มทั้งสองตำแหน่งใช้ action เดียวกัน, ปิดด้วย Escape, keyboard focus และ responsive
- Typecheck ทั้ง backend/frontend, logic tests และ production build ต้องผ่าน
- Integration test ที่ล้าง schema รันได้เฉพาะเมื่อชี้ไป test database ที่ยืนยันว่าแยกจาก production/development

## 9. งานที่อยู่นอกขอบเขต

- ไม่เปลี่ยน geofence ตอนเช็กอินด้วย QR
- ไม่เพิ่มการแก้ไขคำขอลาจากหน้าแอดมิน
- ไม่เพิ่มเสียงแจ้งเตือน
- ไม่เพิ่มหน้ารายละเอียดแบบ URL แยก
- ไม่เปลี่ยนกฎการลาหลายวันซึ่งยังเป็นลาเต็มวันทุกวัน
